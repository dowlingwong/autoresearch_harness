1. **Marker and schemas.** `ENGINE_CONTRACT = "g5_tasl_engine_contract/1"`, `CAMPAIGN_SCHEMA = "trackg_g5_campaign/v1"`,
   `CHUNK_SCHEMA = "trackg_g5_audit_chunk/v1"`, `ROW_SCHEMA = "trackg_g5_audit_row/v1"`. These are the strings that
   `check_engines` greps for.
2. **Invocation.**
   - **Command line:** `python -m autoresearch.trackg.audit_g5 campaign --campaign F --harness-root H --out D
     [--gpu-uuid U]`, or `... audit --chunk F ...`. The job passes `--out <attempt>/out/campaign` or
     `<attempt>/out/audit`.
   - **GPU nodes:** they get `--gpu-uuid`, which is resolved with `gpu_identity.resolve_explicit_on_host` (no
     scheduler variables, `CUDA_VISIBLE_DEVICES` empty).
   - **The CPU-only node** (`noise_floor.CPU_ONLY_NODES`, that is `mlgym_houseprice`) runs without the flag and
     refuses it.
3. **Input validation (fail-closed).** Each input file must have exactly the key set that `campaign_file` or
   `audit_chunk_file` writes. On top of that:
   - `label: EVIDENCE`;
   - relative paths that stay inside the checkout;
   - sha256 pins;
   - a census time in (0, 300] s, with `timeout_factor` 3.0;
   - no isolation waiver;
   - `record_gate: noise_floor.check_effective` and `split_policy: vary`.

   The node spec's name and sha256, the committed-file pin and the data manifest are checked with
   `noise_floor.check_node_pins`. An unisolated node is refused. A test runs every file the paper's
   `campaign_file` writes through this validation.
4. **Seed guards.**
   - **Campaign:** instance k must be one of the file's wave (1–4 or 5–12), with training seed = split seed = manager
     seed = 5100 + k, inside 5101–5112. Each memory mode present must hold exactly the wave's instances.
   - **Audit:** every seed must be in the chunk's K block. K = 10 is 7001–7010. K = 6 is 7001–7003 (label) and
     7006–7008 (evaluation), so 7004, 7005, 7009 and 7010 are refused under K = 6. Each run has training seed = split
     seed = its seed, and a (unit, seed) pair appears at most once.
   - Any other seed, and any K other than 10 or 6, is refused with a "STOP 10" message.
5. **Campaign output.**
   - **Ledgers.** `<out>/instance_<k>_<mode>/campaign_ledger.jsonl` comes from G.4's `run_v2_diff_campaign`
     (`manager_proposal/v2-diff`, `timeout_cap` 2, `max_infra_reruns` 2).
   - **Every executed run** passes the record gate `check_effective`. Every request carries `cache_prompt: false`.
   - **Manager settings.** The seed follows the D26 rule, and the completion cap is 4096. Temperature and memory mode
     come from the file.
   - **Run records** carry `executed`. When executed, they also carry `elapsed_seconds_info_only`.
   - **Campaign record.** `<out>/campaign_record.json` (`trackg_g5_campaign_record/v1`) holds:
     - `stop` and `stop_kind` (item 17);
     - the instances started and their wall seconds;
     - the `memory.events` cgroup used and the deadline rule.
   - **The first instance that STOPs ends the wave.**
6. **A top-level `code_state_sha256` on every ledger run record that has a code state.** `g5_assemble` reads it from
   `runs[-1]`. `G5CampaignRunner` copies it from the diff provenance for a not-run diff, together with
   `code_state_raw_sha256`, and adds `code_state_source: "diff_provenance"`:
   - for a duplicate, it is the state the diff reaches;
   - for an inert diff, it is the incumbent's state;
   - a refused diff with no state in its provenance gets nothing.
7. **Truncation is an invalid proposal** (R1-EXAM-B1-TRUNCATION-INVALID).
   - `TruncationInvalidManager`, a subclass of `V2DiffManager` in `audit_g5.py`, applies it.
   - Rule: `usage.completion_tokens >= max_tokens` makes the reply invalid even if it parses. The call is charged and
     records `truncated: true` and a `parse_error`. This is the job's counting rule, so `truncated_not_invalid` stays 0.
8. **Deadline: no run and no manager call starts that could end past `deadline_epoch` (review M1).** The job kills the
   engine at the deadline, and an isolated run that the engine supervised would outlive it.
   - **Campaign.** `CampaignGuard` makes these checks:
     - before every run, in `G5CampaignRunner.run`: 3 × census + 60 s must fit;
     - before every manager call, in `TruncationInvalidManager.propose`: 120 s more must fit;
     - before every instance.
   - **Audit.** The same run rule applies before every run attempt.
   - **What propagates.** `G5EngineStop` passes through `run_v2_diff_campaign`, which catches only `IntegrityError`
     around runs and `ManagerTransportStop` around calls. The record then gets `stop_kind: "deadline"`.
   - **What a test shows.** A clock-driven test has no run starting after `deadline − 120 s` and no call starting
     after `deadline − 240 s`.
   - **The 120 s allowance** is a G.5 constant. The LLM call itself runs on TASL-7, so a kill during a call leaves no
     process on TASL-2's GPU.
9. **Audit: re-materialisation before any run.**
   - **Baseline unit** (no diffs): it must have the node kit's normalised state.
   - **Any other unit:**
     - the incumbent is the kit plus every diff but the last, each applied with `diff_support.apply_diff`, as the
       campaign did;
     - the kit is copied with the runner's own copy-ignore patterns, and shared prefixes are built once;
     - the last diff must then apply with `write=False` and give the chunk's `code_state_sha256`.
   - **Mismatch.** Any mismatch STOPs the chunk before the first run, with `stop_kind: "integrity"`. So does a run that
     is not executed, or whose recorded state is not the planned one.
10. **Audit runs.** Each run goes through `WorkingCopyRunner`:
    - with training seed = split seed = the audit seed;
    - with `noise_floor`'s limits: census × 3, the job's delegated cgroup, the external memory cap, no waiver;
    - with `evaluated=None` and `keep_code_snapshot=False`.

    The working copy is removed after each run. The record, log and result channel stay.
11. **Rows.** `<out>/rows.jsonl` holds one `trackg_g5_audit_row/v1` row per planned run, in plan order. Each row has:
    - `unit`, `seed`, `train_seed`, `split_seed`, `code_state_sha256` and `executed`;
    - `outcome` with `kind` and `reason`, and a finite float `outcome.value` on every `ok` row, evaluation seeds
      included;
    - the isolation block (`effective`, `waivers`, `exceptions`, `log_intact`, `parent_traced_by`,
      `parent_dumpable_at_accept`);
    - the run id, the record sha256, the frozen-pin sha256 and the elapsed seconds;
    - `attempts`, `infrastructure_reruns`, `earlier_attempts` and `attribution`.

    No row carries the sealed test block.
12. **Infrastructure reruns.**
    - **Rerun rule.** An infrastructure outcome (after attribution, item 13) is rerun up to 2 times.
    - **A later `ok` or `divergent` attempt** becomes the row, with the earlier attempts listed in `earlier_attempts`.
    - **Three infrastructure attempts** give one `infrastructure_failure` row.
    - **A host refusal before a run** (`RunnerError`) counts as an infrastructure attempt. If every attempt fails that
      way, the row has `executed: false` and no isolation block.
    - **`IntegrityError`** STOPs the chunk instead.
13. **Edit-caused failures are divergent, never infrastructure (ruling 1).**
    - **Already divergent in the runner's classifier.** The edited code runs only in the sandboxed worker, so any crash
      of it ends in the frozen parent's non-zero exit:
      - a non-finite loss or metric;
      - a missing metric, or the budget not reached;
      - a measured timeout (`timeout`);
      - a non-zero exit, which includes the worker's death by a signal or by an OOM kill.
    - **Re-attributed by `attribute()`, in audits and, through `G5CampaignRunner`, in campaigns (decision 4).** Three
      infrastructure outcomes become divergent:
      - `oom_kill_memory_limit`: a kill during which both `oom` and `oom_kill` rose in the `memory.events` of the
        cgroup that holds the memory limit (the nearest of `cgroup_parent` and its ancestors whose `memory.max` is
        not `max`, that is the job's `MemoryMax=8G` scope). That scope holds the node wrapper, the G.5 job, this
        engine and the run, and only the run's memory depends on the code state.
      - `crash_signal_repeated`: a synchronous fault signal of the frozen parent (SIGSEGV, SIGBUS, SIGFPE, SIGILL,
        SIGABRT, SIGTRAP, SIGSYS) that recurs on the rerun of the same code state and seed. A first fault stays
        infrastructure and is rerun, since a parent fault can also be a host fault (review m2).
      - `infrastructure_pattern_after_ar_device_repeated`: a default infrastructure log pattern (`No space left on
        device`, `Input/output error`, and so on) whose every match comes after the run's first `AR_DEVICE` line, that
        is in the edited code's phase (review m3), with no default pattern at all before that line (round-2 nit), on
        this attempt **and** on the rerun of the same code state and seed. A first such match stays infrastructure and
        is rerun, since a host I/O fault during training looks the same (round-2 residual); the attribution records
        `edit_phase_pattern: true`. A recurring match is divergent, so an edit still cannot cause an infrastructure
        loop. Node-specific patterns are anchored before `AR_DEVICE` by design, so they stay infrastructure. So does a
        default pattern in a node that never prints `AR_DEVICE`, which is `mlgym_houseprice`.
    - **Disclosure: a persistent host fault.** Both recurrence rules look only at consecutive attempts of the same
      code state and seed. A host fault that persists across two consecutive attempts (minutes apart) therefore gives a
      `crash_signal_repeated` or `infrastructure_pattern_after_ar_device_repeated` row (in campaigns, a
      `discarded_divergent` step). A fault that lasts longer also hits the baseline and parent units, where E5 STOPs the
      node (`baseline_label_divergent_other`). Every such row or run record carries its `attribution` (rule, signal or
      pattern, `crash_signal` / `edit_phase_pattern`), so the T1 report can count these rows and disclose them.
    - **Kept as infrastructure** (and rerun):
      - a kill without evidence that the run caused it (a host-wide OOM raises `oom_kill` without `oom`; an outside
        SIGTERM);
      - a launch error or no exit status;
      - other log patterns;
      - an unreadable `memory.events`, recorded as `"unavailable"`.
    - **Campaign records.** A campaign run whose outcome was re-attributed carries `outcome_attribution` and the new
      outcome. Its state is registered as evaluated, as the runner registers any non-infrastructure run. A campaign
      parent killed at the memory limit is therefore `discarded_divergent` and is audited, instead of
      `infrastructure_failure_final`. This is a disclosed choice, made on the reviewer's recommendation; ruling 1 was
      stated for audit rows. `run_record.json` on disk stays the runner's own record.
14. **Gate refusals** (corrected after review m1).
    - **Effect.** A record that fails `check_effective` STOPs the chunk with `stop_kind: "unisolated"`.
    - **The row.** If the run's kind is `ok` or `divergent`, its row is written first, with its isolation block and
      `gate_refusal`, and without a value.
    - **How the paper's current `read_rows` classes it:**
      - it raises STOP 2 (node class) only when `effective`, `waivers` or `exceptions` fail;
      - a refusal on `log_intact`, `parent_traced_by` or `parent_dumpable_at_accept` alone passes `read_rows`, and the
        job then sees missing rows (or, for the chunk's last run, the engine stop), which is infrastructure class.
    - **Fix needed on the paper side** (§7 item 1): `read_rows` should check those fields, or `gate_refusal`, as well.
15. **The engine's deadline STOP** (item 8) is recorded with `stop_kind: "deadline"`. Today the job classes it as
    infrastructure, because rows are missing or the campaign is short. The paper side will map it to node-class STOP 9
    (§7 item 2).
16. **Members.** The job reads `instance_*/campaign_ledger.jsonl`, its own `out/chunk.json` and `out/audit/rows.jsonl`.
    Everything else under `<out>` stays in `out.tar` unread:
    - run records, which keep the runner's sealed test block, as in G.1b and G.4;
    - logs and result channels;
    - campaign working copies and snapshots, with any binaries.

    `chunk_record.json` (`trackg_g5_audit_chunk_record/v1`) holds:
    - `stop` and `stop_kind`;
    - `written_rows` and `expected_runs`;
    - the limits and the `memory.events` cgroup;
    - the number of units re-materialised.

    The re-materialised state directories are removed at the end.
17. **Stop text and `stop_kind`** (review m4).
    - **What the records carry.** Both records carry `stop` (text naming a cause and a run or unit index, never a metric
      value or a per-seed outcome; round-2 n1) and `stop_kind`.
    - **The values of `stop_kind`:**
      - `refused`: the input file, pins or node, or an engine call refused before running;
      - `deadline`;
      - `integrity`;
      - `unisolated`: a gate refusal; in a campaign, the ledger's `stop_unisolated`;
      - `transport`;
      - `baseline_failed`;
      - `runner`: a host refusal outside a run attempt;
      - `error`: anything else.
    - **Every exception is caught** (in `run_audit`, `run_campaign` and the CLI), so a record is always written.
    - **Exit codes.** An engine refused before running still writes its record and exits 2. A STOPped engine exits 3;
      otherwise it exits 0.

## 6. What the TASL-2 smoke test must check

1. **Binary outputs, unread.** The engines' out trees contain binaries (campaign working copies and snapshots, run
   directories), and the job opens only the named members.
2. **Edit-caused OOM.**
   - **Expected result.** A representative edit that allocates past the scope's 8G gives `divergent`, never
     `infrastructure_failure`:
     - `oom_kill_memory_limit` if the parent was killed;
     - `nonzero_exit` if the worker was killed.
   - **Check:**
     - `memory_events_cgroup` names the scope;
     - `attribution.memory_events` shows `oom` and `oom_kill` rising;
     - the engine, the job and the wrapper survive the kill;
     - which process the kernel picked.
3. **Edit-caused crash.**
   - An edit that raises in the worker gives `divergent` (`nonzero_exit`).
   - A segfaulting worker (`ctypes`) also gives `nonzero_exit`.
4. **Normalised code-state hashes.**
   - On a real campaign, with at least one kept chain of two or more diffs, the re-materialised `code_state_sha256`
     matches the ledger's normalised hashes.
   - `chunk_record.json` has `units_rematerialised` equal to the unit count, and `stop` null.
5. **`outcome.value`.** Every `ok` row, evaluation seeds included, has a finite numeric `outcome.value`. At traindev,
   `g5_seal.reduce_rows` checks this.
6. **Isolation.** Every `ok` and `divergent` row is `effective: true`, with `waivers {}` and `exceptions []`, through the
   real gate.
7. **Infrastructure rows.** One forced infrastructure failure gives one row after 3 attempts. The job turns it into
   STOP 7.
8. **Not-run steps.** A not-run duplicate in a real ledger carries a top-level `code_state_sha256`.
9. **Timing.** Compare against the census (C3, C5).
10. **systemd OOM handling** (review m5). Check each of these:
    - `systemctl --user show <scope> -p OOMPolicy` is `continue` (the default under `Delegate=yes`);
    - the scope's `memory.oom.group` is 0;
    - systemd-oomd (`oomctl`, `ManagedOOMMemoryPressure` on `user@.service`) does not act on the scope. A userspace
      kill leaves `oom` and `oom_kill` unchanged, so an edit-caused memory-pressure kill would be infrastructure and
      would loop.
11. **No orphans.** After a deadline STOP of either engine, and after a deliberate engine kill, the scope has no `ar_*`
    child cgroup with processes left.
12. **The CPU-only node.** One `mlgym_houseprice` job: no `--gpu-uuid`, `CUDA_VISIBLE_DEVICES` empty.
13. **Truncation on the real server.** Every llama-server reply carries `usage.completion_tokens`, and a cut-off reply
    (`finish_reason: length`) has `completion_tokens` = 4096. The truncation rule depends on both.
14. **Disk.** The size of `out/` per campaign wave against free disk. Working copies and snapshots are kept, and the tar
    briefly doubles the space.
15. **The real job path.** One job through the real `g5_job.run_job`, with the `g5` kind of `t1_tasl_node.sh`, in a
    delegated scope.

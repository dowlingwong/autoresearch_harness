## 2. The contract, item by item

The sources are `g5_job.engine_contract()`, `check_engines`, `campaign_file`, `audit_chunk_file`, `read_rows` and
`campaign_diagnostics` (paper branch `mac-g5-code-main-20261123`, `sweep2/t1_tasl/g5_job.py`); `g5_seal.reduce_rows`; the
3b-1 report §2 and its review (ruling 1, n1); the 3b-2 report (`outcome.value`); and the fake engines in
`r1/tests/test_t1_g5_job.py` and `test_t1_g5_seal.py`.

1. **Marker and schemas.** `audit_g5.py` defines `ENGINE_CONTRACT = "g5_tasl_engine_contract/1"`, `CAMPAIGN_SCHEMA =
   "trackg_g5_campaign/v1"`, `CHUNK_SCHEMA = "trackg_g5_audit_chunk/v1"` and `ROW_SCHEMA = "trackg_g5_audit_row/v1"`.
   These are the strings that `check_engines` greps for.
2. **Invocation.** The module is run as `python -m autoresearch.trackg.audit_g5 campaign --campaign F --harness-root H
   --out D [--gpu-uuid U]` or `... audit --chunk F ...`. The job passes `--out <attempt>/out/campaign` or
   `<attempt>/out/audit`. GPU nodes get `--gpu-uuid`, which is resolved with `gpu_identity.resolve_explicit_on_host`
   (no scheduler variables, `CUDA_VISIBLE_DEVICES` empty). A CPU-only node (`noise_floor.CPU_ONLY_NODES`, that is
   `mlgym_houseprice`) runs without the flag and refuses it.
3. **Input validation (fail-closed).** Each input file must have exactly the key set that `campaign_file` or
   `audit_chunk_file` writes. The engine also checks:
   - `label: EVIDENCE`;
   - relative paths inside the checkout;
   - sha256 pins;
   - census time in (0, 300] s, with `timeout_factor` 3.0;
   - no isolation waiver;
   - `record_gate: noise_floor.check_effective` and `split_policy: vary`.

   The node spec name and sha256, the committed-file pin and the data manifest are checked with
   `noise_floor.check_node_pins`. An unisolated node is refused.
4. **Seed guards.**
   - **Campaign:** instance k must belong to the file's wave (1–4 or 5–12), with training seed = split seed = manager
     seed = 5100 + k, inside 5101–5112. Each memory mode present must hold exactly the wave's instances.
   - **Audit:** every run seed must be in the chunk's K block. K = 10 is 7001–7010. K = 6 is 7001–7003 (label) and
     7006–7008 (evaluation), so 7004, 7005, 7009 and 7010 are refused under K = 6. Each run also needs training seed =
     split seed = the seed, and every (unit, seed) at most once.
   - **Other values:** K must be 10 or 6. Any other seed is refused with a "STOP 10" message.
5. **Campaign output.**
   - **Ledgers.** Each instance and memory mode gets `<out>/instance_<k>_<mode>/campaign_ledger.jsonl`, written by the
     unchanged G.4 path (`run_v2_diff_campaign`, `manager_proposal/v2-diff`, `timeout_cap` 2, `max_infra_reruns` 2).
     The record gate `check_effective` runs on every executed run, and every request carries `cache_prompt: false`.
   - **Manager settings.** The manager seed uses the D26 rule. The completion cap is 4096. Temperature and memory mode
     come from the file (`history` shows the last 12 steps; `none` shows none).
   - **Run records** carry `executed` and, when executed, `elapsed_seconds_info_only`. Manager calls carry `request` and
     `usage`.
   - **Campaign record.** `<out>/campaign_record.json` (`trackg_g5_campaign_record/v1`) holds `stop`, the instances
     started and their wall seconds.
   - **Stop order.** The first instance that STOPs ends the wave, as in `pilot_g4`. Its ledger holds the STOP line.
   - **Deadline.** The wave's deadline is checked before each instance starts.
6. **Top-level `code_state_sha256` on every ledger run record that has a code state** (coordinator's point from the
   T1-features author). `g5_assemble` reads a not-run step's state from `runs[-1]["code_state_sha256"]`. The runner
   writes a not-run diff's state only inside `run["diff"]`. The G.5 campaign therefore uses `G5CampaignRunner`, which
   copies `code_state_sha256` and `code_state_raw_sha256` from the diff provenance to the top level of a not-run
   record and marks it `code_state_source: "diff_provenance"`:
   - for a duplicate, this is the state the diff would reach;
   - for an inert diff, it is the incumbent's state;
   - a refused diff whose provenance has no state gets no field.

   Executed runs already carry the field. `run_record.json` on disk is left as the runner wrote it.
7. **Truncation is an invalid proposal** (R1-EXAM-B1-TRUNCATION-INVALID). `TruncationInvalidManager`, a subclass of
   `V2DiffManager` in `audit_g5.py`, turns a reply into an `invalid_proposal` when `usage.completion_tokens >=
   max_tokens`, even if it parses. The call is still charged, records `truncated: true` and a `parse_error`, and nothing
   runs. This is the counting rule of `campaign_counts`, so `truncated_not_invalid` stays 0.
8. **Audit: re-materialisation before any run.**
   - A unit with no diffs must have the node kit's normalised code state.
   - For any other unit, the engine builds the incumbent: the kit plus every diff but the last, each applied with
     `diff_support.apply_diff`, as the campaign did. The kit is copied with the runner's own copy-ignore patterns, and
     shared prefixes are built once. The last diff must then apply (`write=False`) and give the chunk's
     `code_state_sha256`.

   Any mismatch STOPs the chunk before the first run, with `integrity: unit <i>`. During runs, a run that is not
   executed, or whose recorded state differs from the plan, STOPs the chunk as well.
9. **Audit runs.** Each planned (unit, seed) runs through `WorkingCopyRunner` with training seed = split seed = the audit
   seed and the limits `noise_floor` uses: census time × 3, the job's delegated cgroup, the external memory cap, no
   waiver. Settings: `evaluated=None`, `keep_code_snapshot=False`. The working copy is removed after each run. The
   record, log and result channel stay.
10. **Rows.** `<out>/rows.jsonl` holds one `trackg_g5_audit_row/v1` row per planned run, in plan order:
    - `unit`, `seed`, `train_seed`, `split_seed`, `code_state_sha256` and `executed`;
    - `outcome` with `kind` and `reason`, and on `ok` rows a finite float `outcome.value` (the validation metric; also
      at evaluation seeds);
    - the isolation block (`effective`, `waivers`, `exceptions`, `log_intact`, `parent_traced_by`,
      `parent_dumpable_at_accept`), the run id, the record sha256, the frozen-pin sha256 and the elapsed seconds;
    - `attempts`, `infrastructure_reruns`, `earlier_attempts` and `attribution`.

    No row carries the sealed test block.
11. **Infrastructure reruns.** An infrastructure outcome (after attribution, item 12) is rerun up to 2 times. If an
    attempt then gives `ok` or `divergent`, that attempt is the row, and the earlier attempts are listed in
    `earlier_attempts`. If all 3 attempts are infrastructure failures, the run is one `infrastructure_failure` row. A
    `RunnerError` raised by the host before a run counts as an infrastructure attempt; when every attempt fails that
    way, the row has `executed: false` and no isolation block. An `IntegrityError` STOPs the chunk instead.
12. **Edit-caused failures are divergent, never infrastructure (ruling 1).**
    - **Already divergent in the runner's classifier:** a non-finite loss or metric, no metric, the budget not reached,
      a measured timeout (`timeout`), and a non-zero exit. A crash of the edited code in the worker makes the frozen
      parent exit non-zero, and a worker OOM-killed under the scope's limit also ends with the parent's non-zero exit.
    - **Re-attributed by `attribute()`.** The classifier calls a process killed by a signal (or exit 137/143) an
      infrastructure failure. The engine makes two such cases divergent:
      - `oom_kill_memory_limit`: during the run, both `oom` and `oom_kill` rose in the `memory.events` of the cgroup
        that holds the memory limit (the nearest of `cgroup_parent` and its ancestors whose `memory.max` is not
        `max`). That cgroup is the job's `MemoryMax=8G` scope, which holds only the engine and the run.
      - `crash_signal`: a synchronous fault signal of the run's process (SIGSEGV, SIGBUS, SIGFPE, SIGILL, SIGABRT,
        SIGTRAP, SIGSYS).
    - **Kept as infrastructure** (and rerun):
      - a kill without that evidence (a host-wide OOM raises `oom_kill` without `oom`; an outside SIGTERM);
      - a launch error, no exit status, an infrastructure log pattern;
      - an unreadable `memory.events` (recorded as `"unavailable"`).
13. **Gate failures.** A record that fails `check_effective` STOPs the chunk. If its kind is `ok` or `divergent`, its row
    is written first, with the isolation block and without a value, so `read_rows` raises STOP 2 (node class).
14. **Chunk deadline.** A run that cannot finish before `deadline_epoch` (3 × census + 60 s left) STOPs the chunk before
    it starts, as in `noise_floor`. See open question 3.
15. **Chunk record.** `<out>/chunk_record.json` (`trackg_g5_audit_chunk_record/v1`) holds `stop`, `written_rows`,
    `expected_runs`, the limits, the `memory.events` cgroup used and the number of units re-materialised. Re-materialised
    state directories are removed at the end, since they can be rebuilt from the chunk file.
16. **Members.** The job reads `instance_*/campaign_ledger.jsonl`, its own `out/chunk.json` and `out/audit/rows.jsonl`.
    Everything else under `<out>` stays in `out.tar` unread: run records with the runner's sealed test block (as in G.1b
    and G.4), logs, result channels, and campaign working copies and code snapshots with any binaries.
17. **Stop text** names a cause and a run or unit index, never a metric value or a per-seed outcome (round-2 n1). The
    tests check this for a gate STOP. An engine refused before running still writes its record with `stop`, if `--out`
    can be created, and exits 2. A STOPped engine exits 3, otherwise 0.

## 6. What the TASL-2 smoke test must check

1. **Binary outputs, unread.** The engines' out trees contain binaries (campaign working copies and snapshots, run
   directories), and the job opens only the named members.
2. **Edit-caused OOM.** A representative edit that allocates past the scope's 8G must give a `divergent` row with
   reason `oom_kill_memory_limit`, or `nonzero_exit` if the worker rather than the parent was killed. It must never give
   `infrastructure_failure`. Check:
   - `chunk_record.json`'s `memory_events_cgroup` names the scope;
   - the row's `attribution.memory_events` shows `oom` and `oom_kill` rising;
   - the engine and the job survive the kill (see open question 2: systemd's `OOMPolicy`);
   - which process the kernel picked.
3. **Edit-caused crash.** An edit that raises in the worker gives `divergent` (`nonzero_exit`). If possible, add one
   that faults (SIGSEGV via `ctypes`): `divergent` with `crash_signal` (parent) or `nonzero_exit` (worker).
4. **Normalised code-state hashes.** The re-materialised `code_state_sha256` matches the ledger's normalised hashes on a
   real campaign, with at least one kept chain of two or more diffs. `chunk_record.json`: `units_rematerialised` equals
   the unit count and `stop` is null.
5. **`outcome.value`.** Every `ok` row, evaluation seeds included, has a finite numeric `outcome.value`
   (`g5_seal.reduce_rows` checks this at traindev).
6. **Isolation.** Every `ok` and `divergent` row is `effective: true`, with `waivers {}` and `exceptions []`, through the
   real gate.
7. **Infrastructure rows.** One forced infrastructure failure, for example an unavailable sandbox or launch failure,
   gives one row after 3 attempts. The job turns it into STOP 7.
8. **Not-run steps.** A not-run duplicate in a real ledger carries a top-level `code_state_sha256`.
9. **Throughput.** Compare the timing against the census (C3, C5).

## 7. Open questions

1. **Where truncation lives.** `engine_contract()["truncation_invalid_in"]` and the 3b-1 review name
   `manager_v2_diff.py`. The behaviour is built in `audit_g5.py` (`TruncationInvalidManager`), so the existing manager
   and G.4 stay unchanged. `check_engines` does not test the location. The paper side may update the wording; or, if
   the location is binding, a one-flag change in `manager_v2_diff.py` with default off would carry the same rule.
2. **systemd `OOMPolicy` of the job scope (blocking for ruling 1 on the host).** `t1_tasl_node.sh` starts
   `systemd-run --user --scope -p Delegate=yes -p MemoryMax=8G -p MemorySwapMax=0`. If the user manager's
   `DefaultOOMPolicy` (or a scope `OOMPolicy`) is `stop` or `kill`, or `memory.oom.group` is 1, one OOM kill in the
   scope stops the whole scope: job, engine and wrapper. The attempt is then left without a record, and a retry would
   loop. Check on TASL-2 with `systemctl --user show <scope> -p OOMPolicy` and the scope's `memory.oom.group`. If
   needed, the paper's wrapper should add `-p OOMPolicy=continue`.
3. **An engine deadline STOP is infrastructure class on the paper side.** When the engine stops before a run that cannot
   finish (contract item 14), rows are missing. `audit_diagnostics` then classes the chunk "planned audit runs have no
   row", which is infrastructure class and allows a new attempt. Without the guard, the job's subprocess timeout would
   fire instead: node class STOP 9, but it could leave an orphaned run on the GPU. I kept the guard. The paper side may
   map `chunk_record.json` `stop` containing `deadline:` to node class. Until then, the operator should treat a repeated
   deadline STOP as node class.
4. **Campaigns keep G.4's classifier.** In a campaign, a frozen parent killed by a scope OOM becomes
   `infrastructure_failure_final` after 2 reruns. That step is not audited and counts toward STOP 7's share. Ruling 1
   was stated for audit rows. A worker killed by an OOM is already `discarded_divergent`. The same attribution could be
   carried into campaigns through the new `runner_factory` if the author wants it.
5. **Engine killed by the OOM killer.** The engine shares the scope. If the kernel kills the engine rather than the run,
   the chunk has no `chunk_record.json` and the job STOPs as infrastructure. This is unlikely, since the run's RSS
   dominates. The smoke test (item 6.2) should look at it.
6. **Census time cap.** The engine refuses `measured_run_seconds` above 300 s, as `noise_floor` and `pilot_g4` do. The
   slowest current timeout basis is 255.9 s (`autoresearch_fixedtokens`).
7. **Sealed test block on disk.** As in G.1b and G.4, run records under `out/` keep the runner's parsed test metric.
   They go only into `out.tar`, and the job never opens them.
